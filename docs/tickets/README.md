# Tickets

Fourteen tickets, numbered in build order. Next week the model gets **one ticket at a time**, with `progress.md`, `plan.md` and `rules.md` pasted first (`workflow.md`) — never the whole folder.

## The order, and why

1. **01 Project skeleton** — the boring one. Nothing is real until a page loads at a public address.
2. **02 Database tables** — everything else writes to these.
3. **03 Sign up and log in** — the spine starts here.
4. **04 Password reset** — finishes R1 while auth is fresh; also the first real Brevo send.
5. **05 Goal screen**
6. **06 Tasks** — end of the first spine: sign in → set goal → add tasks.
7. **07 Chosen person and confirmation** — the goal can now actually start.
8. **08 Progress, risk and next step** — the dashboard becomes real.
9. **09 The hourly check** — the riskiest piece; tests first.
10. **10 Warning and stop emails** — the consequence, end to end.
11. **11 Goal end** — both finish lines.
12. **12 Empty, loading and error states** — what demo night actually shows first.
13. **13 Demo night prep** — R11, rehearsed.
14. **14 AI next step** — built last, cut first.

## The first three

**01, 02, 03.** The first one is boring on purpose: a deployed page that reads from the database proves the whole free-tier stack before anything is built on it.

## If time runs short

Cut from the bottom, matching `scope.md`: 14 (AI) first, then the learner's own next-step pick inside 08, then task reordering inside 06, then the missed-deadline email inside 11. Tickets 09 and 10 are never cut — they are the product. Record any cut in `decisions.md` with the date and reason.

## The count, honestly

Fourteen tickets, three build weeks: four to five per week. Tight but real, because 01–06 are small and well-trodden; the genuinely hard ones (07, 09, 10) sit mid-list with room around them.
